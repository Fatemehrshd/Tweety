# AGENTS.md — backend

Applies only within `backend/`. Also read the root `AGENTS.md` for repo-wide rules (branching, versioning, architecture characteristics, skills).

## Framework / Application

- Next.js
- TypeScript
- App Router / Route Handlers for HTTP APIs

## Architecture — modular, feature-based
- Code organized by feature, not by technical layer: `modules/<feature>/` (e.g. `modules/auth/`, `modules/orders/`) each holding its own route/controller, service, repository, and schema/DTOs — no global `services/` or `repositories/` folders
- Inside each module: route/controller (parsing + response only) → service (business logic) → repository (DB access) — services never import the ORM/DB client directly
- A module exposes only what other modules need via its `index.ts`; nothing outside the module reaches into its internal files directly
- Cross-module calls go through the other module's exposed service, never straight to its repository or DB tables
- Shared code (utils, base classes, shared types) lives in `modules/shared/` — no feature-specific logic allowed there

## Auth
- Access token: JWT, short-lived (~15min)
- Refresh token: long-lived (~7-30d), stored in an httpOnly + secure cookie — never in localStorage
- Refresh token rotation: issue a new refresh token on every use, invalidate the old one immediately
- Revoked/rotated refresh tokens tracked in Redis, not Postgres — fast lookup, natural TTL expiry
- Passwords hashed with bcrypt, cost factor >= 12

## Database & caching
- Primary DB: PostgreSQL — source of truth
- Migrations are always generated by TypeORM's migration tool, never hand-written raw SQL
- Redis: caching layer + refresh-token/session state — never the source of truth for business data
- Cache invalidation is explicit on write, not TTL-only, for any data that must stay consistent

## Code style
- Every API input validated against a schema before it touches business logic (e.g. Zod, class-validator, or equivalent for the chosen framework)

## Logging & error handling
- All errors go through a central error handler — no silent `catch` blocks
- Structured logging with levels (error/warn/info/debug) via the framework's built-in logger or a dedicated library (e.g. pino, winston) — no bare `console.log` in production code paths
- Never log secrets, tokens, passwords, or full request bodies containing user data
- Every thrown error is an instance of a typed error class, never a raw string

## API documentation

- API documentation uses Swagger / OpenAPI
- Every API route added or changed must have its OpenAPI/Swagger documentation updated in the same change
- Documentation is generated from code/schema, never maintained as a separate manually edited spec
- Swagger documentation must remain synchronized with the actual API implementation

## Performance
- Every list/query endpoint is paginated — no unbounded `SELECT *`
- N+1 queries forbidden — use joins or batched loading
- Hot/expensive reads cached in Redis (see Database & caching)

## Scalability
- Services are stateless — no in-memory session or job state; anything that must persist goes to Postgres or Redis
- Long-running/heavy work (emails, exports, external API batches) goes through a background job queue (e.g. BullMQ + Redis, or equivalent), not inline in the request

## Reliability
- Every external call (payment gateway, SMS, third-party API) has a timeout and a bounded retry with backoff
- Multi-step writes that must succeed/fail together are wrapped in a DB transaction

## Observability
- `/health` endpoint required, checked by the deploy pipeline before a release is marked live
- Every log line includes the request/trace ID (see root Observability rule)

## Boundaries
- Never touch `/migrations` manually
- Auth logic lives only in `modules/auth/*`, don't duplicate elsewhere
- API routes must return typed responses (see `modules/shared/api-types.ts`)
